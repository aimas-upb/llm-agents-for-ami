# SimuHome mapping tables

Generated by `tests/simuhome/td/convert.py --phase-a`. These eight files are the
**human artifact** of Phase A: the semantics that Matter cannot supply on its own.
Edit them, then run Phase B.

## The `status` field

Every row carries one of:

| status | meaning | on rerun |
|---|---|---|
| `auto` | fully determined by the vendored Matter registry or by unambiguous input structure | regenerated wholesale |
| `review` | a defensible heuristic value that encodes judgement — populated, but confirm it | machine fields refreshed, your values kept |
| `todo` | could not be decided; **must** be filled before Phase B | same as `review` |
| `approved` | you have confirmed this row | **preserved verbatim** |

Set `status: approved` to lock a row. If the corpus or registry later disagrees
with an approved row, the generator records the difference under `_drift` and
reports it rather than overwriting your decision. Rows whose key disappears from
the corpus are kept and flagged `_orphaned` — never silently deleted.

Phase B refuses to run while any `todo` remains.

## What to scrutinise first

**`actuation_effects.yaml`.** It encodes which environmental variable each command
moves and in which direction. The seeds come from the benchmark-validated overrides
in `run_simuhome_e2e.py::_scenario_tdsosa_hints`, so e.g. an air purifier switched
**on** *decreases* `air_quality` (pm10 falls) — the opposite of what a service-name
heuristic would guess. `Off` commands invert their family's direction.

`monotonic: false` with `direction: null` is deliberate, not missing data: toggles
and level/percent setters have no inherent direction, matching how the repo already
treats setpoint services (`hasp.py::_SETPOINT_SERVICES`).

## Properties are instances, not shared classes

`tdsosa:affordsProperty` points at an **anonymous node** typed by the class in
`property_type` — never at a shared class IRI. Home Assistant fixes no value
range per device type (the climate entities in this benchmark carry 42 distinct
`min_temp` and 70 distinct `max_temp` values), so limits describe one deployed
device, not a type. Two TVs with different brightness ranges are two instances
of `ex:TvBrightness`.

The class hierarchy (`ex:TvBrightness rdfs:subClassOf ex:LevelControlBrightness`)
still stands on its own, in `out/vocab/ex.ttl` — as `rdf:type` targets only. Each
TD stays self-contained: it references no node defined outside itself, and two
devices affecting the same room say so by naming the same
`sosa:FeatureOfInterest`, not by sharing a property node.

**Carried into Phase B** (see the `phase_b()` docstring in `convert.py`):

1. *Per-instance limits.* Because the tables are type-level, they cannot supply
   them. Phase B must read the per-episode HA YAML for `min_temp` / `max_temp` /
   `target_temp_step`, the `sensor_metadata` rows (`Min`/`MaxLevel`,
   `Min`/`MaxMeasuredValue`), and `FanControl.FanModeSequence` — which declares
   which fan modes *this* device supports — to populate each blank node.
   Treat `FanModeSequence` as advisory: the corpus contradicts it (see the
   anomalies section of `out/reports/inventory.md`), so action inputs should use
   the `enum` in `ha_binding.yaml` while `FanModeSequence` is emitted alongside
   as a capability statement.
2. *One type per node.* Emit only the most specific class —
   `[ a ex:DimmableLightOnOff ]`, never `[ a ex:DimmableLightOnOff,
   sosa:ActuatableProperty ]`. The parent is entailed by `ex.ttl` and,
   independently, by the v2 ontology's `someValuesFrom` restriction on
   `tdsosa:ActuatablePropertyAffordance`. The only exceptions are `td:Thing`
   (spec-required) and the `sosa:Sensor` / `sosa:Actuator` role.

## Vocabulary

Terms are drawn from `dev/ontologies/td-sosa-extension-v2.ttl` — 4 classes
(`ObservablePropertyAffordance`, `ActuatablePropertyAffordance`,
`IncreasingActuation`, `DecreasingActuation`) and 6 object properties
(`hasEffectActuation`, `affordsProperty`, `amount`, `affectsObservableProperty`,
`increasesObservableProperty`, `decreasesObservableProperty`). `verify.py` asserts
that nothing outside that set is referenced.

Note both action-side links are emitted in Phase B: `sosa:actsOnProperty` for the
knob (an `sosa:ActuatableProperty`) and `tdsosa:affectsObservableProperty` for the
environment (an `sosa:ObservableProperty`). They are different roles, and the
existing SPARQL in `hasp_cache.py` matches on the former.

## Rerunning

```bash
python tests/simuhome/td/convert.py --phase-a      # regenerate, preserving edits
python tests/simuhome/td/verify.py                 # 32 checks
```

`--no-timestamp` omits `generated_at_utc` for byte-identical CI runs; `--no-cache`
ignores the memoised scan; `--no-json` skips the one-time `ProductName` lookup.
